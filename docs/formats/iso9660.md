# ISO 9660, as far as we rely on it

What `engine/source/discReader.c` assumes, and how much of it has been checked.
Claims are marked **verified** when this project has confirmed them against a
real image, and **assumed** when they come from the specification or common
practice and nothing here has tested them yet. Do not promote one to the other
without adding a check.

## Why the engine reads discs at all

We ship no game data. A copy of the game is supplied at run time, and a disc
image is the form it usually takes — especially in a browser, where there is no
other way to hand the engine a game. The reader is in the engine rather than in
tooling so there is one implementation: `tools/vic-extractor` calls this same C
over a foreign function interface, as it already does for the package reader.

## Layout

**verified.** The first 16 sectors (32 KiB) are reserved and carry nothing we
read. Volume descriptors begin at sector 16, one per 2048-byte sector, and each
starts with a one-byte type followed by the five characters `CD001`. The set
ends with a descriptor of type 255.

- type 1 — primary volume descriptor
- type 2 — supplementary volume descriptor, which is where Joliet lives
- type 255 — terminator

**verified.** The volume identifier is 32 bytes at offset 40 of the primary
descriptor, space padded.

**verified.** A directory record for the root sits at offset 156 of a
descriptor, in the same 34-byte layout as any other directory record.

## Directory records

**verified.** A record is variable length, and the first byte is that length. A
length of zero means the rest of the sector is padding: records never straddle a
sector boundary, so a reader skips to the next sector rather than stopping.

Within a record:

| offset | size | meaning |
| --- | --- | --- |
| 0 | 1 | record length |
| 2 | 4 | extent, in sectors, little endian |
| 10 | 4 | data length in bytes, little endian |
| 25 | 1 | file flags; bit 1 (0x02) marks a directory |
| 32 | 1 | identifier length |
| 33 | n | identifier |

**verified.** Both the extent and the data length are stored twice, little
endian then big endian. We read the little endian copy and ignore the other.

**verified.** An identifier of a single byte `0x00` or `0x01` is `.` or `..`.

**verified.** File identifiers carry a `;1` version suffix, which is stripped.
Directory identifiers do not carry one.

## Joliet

**verified.** A supplementary descriptor is a Joliet one when the three bytes at
offset 88 are `%/@`, `%/C` or `%/E` — the three UCS-2 levels. Retail discs carry
both trees, and the Joliet one holds the real file names rather than 8.3
truncations, so it is preferred wherever present.

**verified.** Joliet identifiers are UCS-2 big endian. We decode to UTF-8.

**assumed.** Nothing above the basic multilingual plane appears. UCS-2 cannot
encode it and a disc from 2004 has no reason to try, but this is not checked —
a surrogate pair would be decoded as two replacement-shaped code points rather
than rejected.

## What is deliberately not read

- **The path table.** It is a faster index into the directory tree, and it is
  redundant: walking the records reaches every file. Reading both would mean
  reconciling them when they disagree.
- **Rock Ridge extensions.** Long names, permissions and symbolic links. Retail
  Windows discs do not carry them, and Joliet already gives us real names.
- **Multi-extent files.** A file over 4 GiB is split across records with the
  multi-extent flag set. Nothing on a Sims 2 disc is close, and a reader that
  half-supported it would silently return the first fragment.
- **Multi-session and mixed-mode discs.** The image is assumed to be one
  session of 2048-byte data sectors. A raw 2352-byte-per-sector rip will be
  rejected as not an ISO rather than misread.

## Limits the reader imposes

These are ours, not the format's:

- 320 bytes for one path, and 128 bytes per file for the pool they share.
- 128 KiB for one directory's records, which is upwards of a thousand entries
  in a single directory.
- 512 directories waiting to be walked, and 32 levels of nesting.
- A catalogue size the caller chooses.

Each has its own status so a disc that exceeds one says which, rather than
appearing to hold fewer files than it does.
